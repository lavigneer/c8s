# Documentation Practices

Guidelines for what gets committed to the repo and what stays in Claude conversations.

## What NOT to Commit

### Progress Reports and Status Files (General)
- ❌ `PROGRESS.md` - Task completion tracking
- ❌ `STATUS.md` - Current work status
- ❌ `CHANGELOG.md` (unless project-established) - Git history is your changelog
- ❌ Detailed progress/phase tracking files (outside of spec/)

These are useful for Claude to communicate during a session, but don't need long-term storage in the repo.

### Exception: spec/ Directory
- ✅ **All files in `spec/` directory ARE committed** - This is where spec-kit framework generates specifications
- ✅ `spec/spec.md` - Feature specification
- ✅ `spec/plan.md` - Implementation plan
- ✅ `spec/tasks.md` - Task breakdown
- ✅ `spec/constitution.md` - Project constitution
- ✅ Other spec-kit generated files

These are part of the spec-driven development workflow and should be committed as they're updated.

### Code Comments for Progress
- ❌ `// TODO: implement X` without context
- ❌ Comments tracking what Claude did or why
- ❌ In-progress comments explaining temporary workarounds
- ❌ Comments documenting the development process

These clutter the codebase and become stale quickly.

### Session-Specific Documents
- ❌ Claude's notes about the implementation
- ❌ Task breakdowns created for a single session
- ❌ Temporary debugging notes
- ❌ Session summaries

## What TO Commit

### Essential Documentation
- ✅ `README.md` - Project overview and setup
- ✅ `CLAUDE.md` - Development guidelines (checked in)
- ✅ Architecture documentation
- ✅ Design decisions (ADRs if using that pattern)
- ✅ API documentation
- ✅ Setup and configuration guides

### In-Code Documentation
- ✅ Godoc comments for exported functions/types
- ✅ Comments explaining **why** code does something non-obvious
- ✅ Comments for complex algorithms or business logic
- ✅ Package-level documentation
- ✅ Comments explaining design patterns used

### Build and Process Documentation
- ✅ `CLAUDE.md` - Development workflow, tools, and best practices
- ✅ `Makefile` - Build automation targets and help
- ✅ `.claude/skills/` - Reusable workflows and procedures
- ✅ `.claude/commands/` - Custom slash commands
- ✅ `spec/` directory - All spec-kit generated files (spec.md, plan.md, tasks.md, constitution.md, etc.)

## Communication vs. Documentation

**During a Claude session** (fine to show, don't commit):
- Progress updates on what's being implemented
- Phase breakdowns and task tracking
- Status reports
- Debugging notes and investigation results
- Implementation rationale

**Long-term repo documentation** (commit these):
- Final architecture decisions
- How to build/test/deploy (in CLAUDE.md and skills)
- API contracts and interfaces
- User-facing features and capabilities
- Setup instructions

## Best Practice Examples

### ❌ Don't Commit This
```go
// Claude is implementing feature X in phase 1
// This struct holds pipeline configuration
// TODO: Add validation for branches field
type PipelineConfig struct {
    Branches []string
}
```

### ✅ Commit This
```go
// PipelineConfig defines a CI/CD pipeline for a repository.
// Branches can use glob patterns (e.g., "main", "feature/*")
// for flexible branch targeting.
type PipelineConfig struct {
    // Branches specifies which branches trigger this pipeline.
    // Supports glob patterns. Required field.
    Branches []string
}
```

## When in Doubt
- **Is this for someone building/using this project?** → Commit it
- **Is this tracking work progress?** → Don't commit it (unless in spec/)
- **Will this be outdated in a week?** → Don't commit it
- **Is this explaining non-obvious code?** → Commit it
- **Is this a session-specific note?** → Don't commit it (unless generated by spec-kit)
- **Is this in the spec/ directory and generated by spec-kit?** → Commit it

## Special Cases

### Makefile and Skills
- These ARE committed because they're reusable workflows
- Update them as you learn better practices
- They're the "institutional memory" of how to work on the project

### CLAUDE.md
- This IS committed because it documents the development process
- Update it when tools, versions, or major workflows change
- Links to feature implementations but doesn't document individual sessions

### spec/ Directory (Spec-Kit Generated)
- All files in `spec/` ARE committed as they're generated/updated by spec-kit
- `spec.md` - Evolving specification for current feature
- `plan.md` - Implementation plan and breakdown
- `tasks.md` - Actionable task list
- `constitution.md` - Project principles and standards
- These form the spec-driven development record and should be tracked in git

### README and Guides
- Commit high-level overview and setup
- Link to CLAUDE.md for detailed development info
- Don't duplicate information between files
